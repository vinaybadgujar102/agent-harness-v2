Lesson 0005

When turn 2 is still requires_action

Not every loop ends with assistant prose. Sometimes the model chains tools.

Lesson 0004 · Harness events · Batch loop today

One agent loop, many provider streams

Your batch agent already does while (true) { converse → tool? → continue }. Streaming does not change the count of tools — only how many streams you open before the user sees a final answer. 

Stream 1 → tool_call_ready(A) → requires_action
  execute A → function_result(A)

Stream 2 → tool_call_ready(B) → requires_action   ← turn 2, still not "done"
  execute B → function_result(B)

Stream 3 → text_delta* → completed               ← finally message_complete

What accumulates in input

Stateless history grows each round:

user_input
function_result   (for call A)
function_result   (for call B)
…

Note: your adapter today sends user_input and function_result steps from Conversation turns. The model inferred prior function_calls from context in the interaction; if a provider ever drops that, you would also persist call steps — not needed for your current Google spike pattern.

Harness events across the loop

Per stream: turn_started → … → tool_call_ready OR message_complete
            → turn_completed(requires_action | completed)

Between streams (agent only):
  tool_run_started → tool_run_finished

UI pattern: show a timeline — “Running bash…”, “Running bash…”, then stream assistant text. Each requires_action is a checkpoint, not an error.

When models chain tools

  • First tool output is input to deciding the second command.
  • Plan-and-act prompts (“inspect, then fix”) often need 2+ calls.
  • Each stream may include a thought step before the next call.

Termination

Loop stops when a stream yields message_complete and turn_completed({ status: "completed" }) — no tool_call_ready on that stream. Same stop rule as batch InteractionStep.message.

Quiz

Ask the agent how many streams a “todo app” prompt might need — estimate only, no coding.
