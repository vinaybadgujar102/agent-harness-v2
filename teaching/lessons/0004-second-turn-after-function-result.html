Second turn after function_result

Turn 1 ended with requires_action. Turn 2 is a new streamed interactions.create with richer input.

Lesson 0003 · Harness events · Gemini loop notes

What you add to input

Same stateless rule as batch: keep full conversation as Interactions steps. After executing the tool locally, append one step: 

{
  type: "function_result",
  name: "bash_tool",
  call_id: "<id from function_call step>",
  result: [{ type: "text", text: "<JSON string of tool output>" }]
}

Your harness already maps this from Conversation.addToolResult via toGoogleSteps — same payload for stream and non-stream.

Turn 1 vs turn 2 (harness events)

Turn 1 (you ran --tools spike)
  turn_started → tool_call_ready → turn_completed(requires_action)

Agent executes bash locally → tool_run_finished

Turn 2 (new stream, input includes user + function_result)
  turn_started                    ← new interaction.id
  (thought step may appear again)
  model_output → text_delta*      ← usual assistant reply
  message_complete
  turn_completed(completed)       ← not requires_action if done

Primary doc: Interactions API (function calling section). In-repo flow diagram: learning doc step 7–8.

Common turn-2 outcomes

  • Final answer — model_output streams text; status: "completed".
  • Another tool — another function_call step; requires_action again; loop continues.
  • Failure — failed / error harness event; tool stderr often already in function_result.

Two-turn story (one agent loop iteration)

User: "Run bash_tool echo hello"
  Stream A → tool_call_ready(echo …) → requires_action
  Execute → stdout "hello\n"
  Stream B input adds function_result with that stdout
  Stream B → text_delta "The command printed hello…"
           → completed
