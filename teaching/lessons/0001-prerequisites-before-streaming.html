Lesson 0001 · Mission: streaming harness

Prerequisites before you change code

One win: you can name the four decisions and the batch gate rule.

Links: Harness today, Glossary, Mission

1. Read this first (primary source)

Google documents the streaming model your default provider will use: Streaming interactions. Skim event order: interaction.created → steps → interaction.completed.

2. Four decisions (checklist)

A. What you stream outward

Minimum for UX: assistant text_delta. Strongly consider: tool_call_started, tool_result, turn_complete. Usually skip streaming raw vendor JSON.

B. Internal contract

Replace “only Promise<InteractionStep>” with something like AsyncIterable<HarnessEvent> per converse call, still ending in a complete step for tools. See glossary.

C. Provider parity plan

Google: interactions.create({ stream: true }) + SSE. OpenAI: chat completion stream + tool fragment accumulator. Anthropic: message stream events. Same harness events from three parsers.

D. Transport to the user

CLI can print deltas to stdout now. Product UI later: HTTP SSE via Bun.serve is a common fit. Pick later; parsers should not depend on transport.

3. Batch gate (non-negotiable)

Tool args may arrive as chunks (arguments_delta on Gemini). Accumulate → parse → validate → then tool.execute. Streaming changes visibility, not safety.

4. Concrete prerequisites in this repo

  • Agree harness event enum (5–8 variants).
  • Document mapping table: Google / OpenAI / Anthropic → harness events.
  • Decide: stream only final assistant message, or also status between tool rounds.
  • Spike Google stream in isolation (script, not refactor) to see thought steps.
  • Plan tests: golden event sequences from recorded SSE fixtures.

6. What not to do yet

Do not rewrite all three providers at once. Do not attach SSE to HTTP before the harness event model exists. Do not stream tool stdout until bash tool semantics are defined.
